Prism / Lesson 0002 / 约 9 分钟

刷新以后，为什么还是同一个 Run？

这节课只回答一个问题：旧页面和旧 JavaScript 内存都不可靠，Prism 如何用磁盘上的事实重建同一个 dossier？学完后，你应该能指出 重建的输入、投影函数和拒绝损坏数据的位置。

01 / 先拆掉一个错觉

导航触发重读；导航本身不保存 Run。

  1. CREATE POST
    返回持久化后的 runId
  2. NAVIGATE router.push
    打开 /runs/:runId
  3. REFRESH Server Page
    再次请求 dossier
  4. REBUILD loadRun
    从磁盘重放事实
  5. HYDRATE initialData
    交给客户端查询

创建成功后，composer 会导航并刷新页面；真正的重新读取发生在 RunDossierPage：Server Component 用 URL 中的 runId 调用 getRunDossier。浏览器 Query cache 可以全部消失，服务器仍可从同一数据目录开始。

02 / 真正的恢复算法

loadRun 不把 snapshot cache 当事实。

const manifest = await this.loadManifest(runId)
const events = readAndValidateEveryJournalLine()
const snapshot = projectRunEvents(manifest, events)

await this.verifyManifestRequest(manifest)
await Promise.all(
  snapshot.artifacts
    .filter((artifact) => !sameValue(artifact, manifest.requestArtifact))
    .map((artifact) => this.readArtifact(artifact))
)
await this.repairSnapshotCache(runDirectory, snapshot)

顺序很关键：先读并校验 immutable manifest，再逐行解析 events.jsonl，然后从空投影重建 snapshot。只有投影完成后， 才验证 request artifact 的长度与 SHA-256、把它解析回 RepairRequest 并与 manifest.request 精确比较；其余 artifact 同样按 hash 验真，最后才比较或修复 snapshot.json。

因此 snapshot.json 是可替换的加速缓存，不是恢复输入。 它唯一的 fail-closed 辅助作用是：若缓存曾见证更大的 lastSequence，而 journal 现在更短，Prism 会拒绝降级， 绝不会拿缓存内容补造事件。 真实实现见 FileTrajectoryStore.loadRun 与 repairSnapshotCache。

03 / 为什么重放结果不会漂

投影每次都从 null 开始。

允许成为输入的事实

  • Manifest：Run ID、创建时间、原始 request、request artifact。
  • Journal：同一 Run 的连续序列事件。
  • Artifact bytes：长度与 SHA-256 必须匹配引用。

不能冒充事实的状态

  • 旧 React state。
  • 旧 TanStack Query cache。
  • Zustand 的状态筛选器。
  • 旧的 snapshot.json 内容。

projectRunEvents 先令 snapshot = null，要求第一条是 sequence 1 的 run.created，再按 2、3、4……连续应用事件。 当前初始 journal 的第二条是 run.queued，所以重建结果是 status: "queued"、lastSequence: 2。跳号、错 Run 或 terminal state 后还有事件，都会变成 corrupt_event，而不是被跳过。

04 / 测试就是可执行故事

“新 store 实例”排除了旧内存。

const created = await store.createRun(request)

const reopened = new FileTrajectoryStore({ dataDirectory })
expect(await reopened.loadRun(runId)).toEqual(created)

这段测试故意不用原来的 store 实例。新实例只知道 dataDirectory 和 runId；若结果仍与创建时完全相同， 恢复依赖的就是落盘的 manifest、journal 和 artifacts，而不是进程内对象。

打开 trajectory-store reopen test 看完整断言；再看 web repository reopen test 如何证明原始 prompt、queued 状态和 journal #2 都能重新出现。

06 / 一句话复述

你现在需要记住什么？

刷新不是“找回前端状态”，而是用 runId 重新读取 manifest 与 journal、 重放 snapshot、验真 artifacts，再把可信 dossier 交给前端。
