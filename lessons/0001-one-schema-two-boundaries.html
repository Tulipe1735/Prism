Prism / Lesson 0001 / 约 8 分钟

一份 Schema，为什么要验证两次？

这节课只追踪一个真实动作：你在 Field Desk 输入一句 repair request，直到页面显示 Validated。目标不是记 API，而是能说出 每一道信任边界在防什么。

01 / 先看整条调用链

五个文件角色，不是五份事实。

  1. SERVER ENTRY page.tsx
    给浏览器可序列化的 workspace 与 viewport
  2. CLIENT ENTRY RepairComposer
    接收输入与交互状态
  3. ONE CONTRACT repairRequestSchema
    定义唯一可接受的数据形状
  4. SERVER GATE route.ts
    不信任浏览器，独立再验一次
  5. TRUSTED RESULT response schema
    浏览器连成功响应也不盲信

apps/web/app/page.tsx → components/field-desk/repair-composer.tsx → packages/contracts/src/index.ts → app/api/repair-requests/route.ts

02 / 第一条关键规则

共享的是规则，不是信任。

浏览器用 safeParse 是为了即时反馈：错误输入不发 request。服务器再用同一个 schema，是为了安全边界：调用者可能 绕过页面，直接 POST。 

// 浏览器：改善体验，但不能建立服务端信任
const parsedDraft = repairRequestSchema.safeParse(draft)
if (!parsedDraft.success) return

// 服务器：重新从 unknown 开始
const parsedRequest = repairRequestSchema.safeParse(input)
if (!parsedRequest.success) return errorResponse(422, ...)

Zod 官方把 safeParse 定义为返回成功或错误结果的普通对象，因此这里 可以显式分支，而不靠异常控制正常校验流程。 查看 Zod 官方说明。

03 / 第二条关键规则

Validated 不是 Run。

现在已经发生

  • 媒体类型、body 大小、JSON 均通过。
  • request 符合 v1 Zod contract。
  • workspace path 属于服务端配置边界。
  • 响应本身符合 validation schema。

现在还没有发生

  • 没有生成 Run ID。
  • 没有 manifest、journal 或 snapshot。
  • 没有 Pi、UI-TARS、patch 或 browser evidence。
  • 刷新后没有任何“运行中”状态需要恢复。

这正是首页坚持显示 “No Runs yet” 的原因：UI 只展示当前实现已经拥有的事实。 Route Handler 使用标准 Web Request/Response API；参见 Next.js 官方 Route Handler 文档。

04 / 检索练习

如果要新增字段，你先改哪里？

假设 repair request 要新增必填字段 targetRoute: "/settings"。请先不看答案，说出最小红→绿顺序。

  1. 先在 contract test 加合法值、缺失值和错误值，确认测试变红。
  2. 只在共享 schema 增加字段，让 contract test 转绿。
  3. 更新 composer 产生的 draft；浏览器边界随同一 schema 生效。
  4. 更新 route test；服务器不需要复制字段规则，仍复用同一 schema。
  5. 跑 typecheck、单测、全测和 production build。
05 / 一句话复述

你应该带走什么？

同一份 schema 消除规则漂移；两次验证守住两道不同的信任边界；只有持久化 ticket 才能把 validated request 变成 Run。

快速复习请打开 Prism validation boundary 参考卡。如果某一跳不清楚，直接问 agent，并带上对应文件或测试名。
